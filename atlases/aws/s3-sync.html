How aws s3 sync decides what to send, skip, and delete

A sync lists both sides, filters both lists, walks them together pairing names, and asks one rule per pair whether to transfer. The rule reads two things, the size and the modification time, never the contents, and it is not the same in each direction: on a download a file is fetched again only when the local copy is newer than the object. The installed help states the download rule two ways that disagree; the source settles which one runs (§8).

The sync subcommand of the AWS CLI's high-level s3 commands: its path forms, listing, filters, pairing, the sync strategies and the flags that replace them, what follows from them, the transfer settings it shares with cp, mv, and rm, and its exit codes.

§1

What sync is

factkindsource
"Syncs directories and S3 prefixes. Recursively copies new and updated files from the source directory to the destination. Only creates folders in the destination if they contain one or more files."documentedH1 · DESCRIPTION; C4 · SyncCommand
Three path forms: <LocalPath> <S3Uri>, <S3Uri> <LocalPath>, <S3Uri> <S3Uri>. The CLI names them locals3, s3local, s3s3 and translates them to the operation names upload, download, copy; those names are what the decision rule branches on (§6). Local to local is refused.documentedH1 · SYNOPSIS; C4 · run, cmd_translation, template_type
Sync is always a directory or prefix operation: "Adding or omitting a forward slash or back slash to the end of any path argument, depending on its type, does not affect the results of the operation." The source sets dir_op to true for sync.documentedH2 · Directory and S3 Prefix Operations; C4 · CommandParameters
On an upload the local source must exist (The user-provided path … does not exist.); on a download a missing local destination directory is created.documentedC4 · add_paths
A directory bucket (S3 Express One Zone) is refused on either side: Cannot use sync command with a directory bucket.documentedC4 · _validate_not_s3_express_bucket_for_sync
--dryrun "Displays the operations that would be performed using the specified command without actually running them." It is the way to see the decision for a given tree before trusting it.documentedH1 · --dryrun

§2

The pipeline

The stages a sync runs, in the order create_instructions appends them. The source and the destination each get a file generator and a filter; the comparator takes both streams and hands one on.

1file_generatorTwo generators: the source, listed with the source client and the operation name; the destination, listed with the destination client and no operation name (§3).
2filtersOne filter per stream, built from the same --exclude and --include list; skipped when no filter was given (§4).
3comparatorPresent only for sync: it walks both streams together and yields the source files to transfer and, with --delete, the destination files to delete (§5, §6).
4file_info_builderTurns each yielded item into the record the transfer stage takes.
5s3_handlerThe transfer client runs the operations concurrently under the settings of §9 and counts failures and warnings for the exit code (§10).
factkindsource
The order and the condition, verbatim: self.instructions.append('file_generator'); if self.parameters.get('filters'): self.instructions.append('filters'); if self.cmd == 'sync': self.instructions.append('comparator'); then 'file_info_builder' and 's3_handler'. So cp --recursive runs the same pipeline without the comparator: it transfers every listed file.documentedC4 · create_instructions
For sync the command table pairs the stages: 'file_generator': [file_generator, rev_generator], 'filters': [create_filter(...), create_filter(...)], 'comparator': [Comparator(**sync_strategies)]. A stage with two components runs one per stream; the comparator, one component, is called with both.documentedC4 · run

§3

Listing both sides

factkindsource
The local side is walked depth-first with os.listdir, one directory at a time. A directory's name gets a trailing separator before the sort, and the sort normalizes the separator to / (names.sort(key=lambda item: item.replace(os_sep, character))), so the local order matches the order of S3 keys: a/b.txt sorts as the key a/b.txt would. The code's own comment: "We need to list files in byte order based on the full expanded path of the key".documentedC5 · list_files, normalize_sort
Symbolic links are followed by default; "S3 does not support symbolic links, so the contents of the link target are uploaded under the name of the link." --no-follow-symlinks skips links on an upload; on a download it "skips any object whose destination is a symbolic link, or is located under one".documentedH1 · --follow-symlinks; C5 · should_ignore_file
Skipped with a warning, not an error: a file that does not exist by the time it is read; a character or block device, FIFO, or socket; a file or directory that is not readable; a name that cannot be decoded. A warning sets the exit code to 2 (§10).documentedC5 · triggers_warning, should_ignore_file_with_decoding_warnings
A local file whose timestamp cannot be read is given the epoch as its time, with the warning "File has an invalid timestamp. Passing epoch time as timestamp." It is not skipped, so on an upload it compares as older than any object.documentedC5 · _validate_update_time
The S3 side is listed through the CLI's BucketLister with the bucket, the prefix, and the page size; --page-size "The default value is 1000 (the maximum allowed). Using a lower value may help if an operation times out." Each object brings its Size and LastModified.documentedC5 · list_objects; H1 · --page-size
A zero-byte key ending in /, the marker the console creates for a "folder", is dropped from the listing for every operation but delete. A sync never copies such markers, which is the source's side of "Only creates folders in the destination if they contain one or more files".documentedC5 · list_objects
The listing order on the S3 side is the API's: the comparator's docstring says both sides are "listed in the same order, least to greatest in collation order". BucketLister, which calls ListObjectsV2, was not read, and S3's own statement of its key order is not on this page.unverifiedC3 · Comparator.call docstring

§4

Filters

factkindsource
"by default, all files are included. This means that providing only an --include filter will not change what files are transferred. --include will only re-include files that have been excluded from an --exclude filter." To send only .jpg files: --exclude "*" --include "*.jpg".documentedH2 · Use of Exclude and Include Filters
"the filters that appear later in the command take precedence over filters that appear earlier." In the source each matching pattern overwrites the verdict of the ones before it; the last match decides.documentedH2; C6 · call
Patterns are not relative. Each is joined to the source root, the absolute local directory or bucket/prefix, and the full path is matched with Python's fnmatch.fnmatch. The symbols are *, ?, [sequence], [!sequence].documentedH2; C6 · _full_path_patterns, _match_pattern
A pattern is also joined to the destination root and tried against each file, so the same filter list applies to the destination listing. That is what makes "files excluded by filters are excluded from deletion" hold for --delete.documentedC6 · call, dst_patterns; H1 · --delete
* crosses directory separators: fnmatch('/tmp/foo/a/b/c.txt', '/tmp/foo/*.txt') is True. So --exclude "*.txt" reaches every depth, and --exclude "a/*" excludes everything under a/, however deep.observedO1 · Python 3.15.2

§5

Pairing the two lists

factkindsource
The comparator takes the next item from each stream and compares their keys. Equal: the pair goes to the file at source and destination strategy, and the source file is yielded if it says so. Source key less: the file is only at the source; the file not at destination strategy decides, and only the source stream advances. Source key greater: the file is only at the destination; the file not at source strategy decides, and only the destination stream advances. When one stream ends, the rest of the other goes to its one-sided strategy.documentedC3 · call, compare_comp_key
The comparator does not sort. "The key concept in this function is that no matter the type of where the files are coming from, they are listed in the same order, least to greatest in collation order." A difference in order between the two listings would pair the wrong names; the shared sort of §3 is what prevents it.documentedC3 · call docstring
The three slots and their defaults: at both, SizeAndLastModifiedSync; not at destination, MissingFileSync (or CaseConflictSync on a download with --case-conflict other than ignore); not at source, NeverSync.documentedC4 · choose_sync_strategies
A flag replaces a slot. Each flag's strategy class adds its option to the sync command through the building-arg-table.s3_sync event and, when the option is set, answers the choosing-s3-sync-strategy event with itself; it takes the slot its sync_type names. This is why --delete, --size-only, and --exact-timestamps are not in the sync command's own option table.documentedC1 · BaseSync.register_strategy; C4 · choose_sync_strategies
Term. A sync strategy is the class that answers "transfer or not" for one slot: the pair, the source-only file, or the destination-only file. The source's name; this atlas uses it the same way.

§6

The decision, by direction and flag

The default rule, SizeAndLastModifiedSync, transfers when (not same_size) or (not same_last_modified_time). The time half, verbatim from the source:

    def compare_time(self, src_file, dest_file):
        src_time = src_file.last_update
        dest_time = dest_file.last_update
        delta = dest_time - src_time
        cmd = src_file.operation_name
        if cmd == "upload" or cmd == "copy":
            if self.total_seconds(delta) >= 0:
                # Destination is newer than source.
                return True
            else:
                # Destination is older than source, so
                # we have a more recently updated file
                # at the source location.
                return False
        elif cmd == "download":
            if self.total_seconds(delta) <= 0:
                return True
            else:
                # delta is positive, so the destination
                # is newer than the source.
                return False

(C1 · compare_time, docstring left out.) True means "same enough, no transfer". On a download the destination is the local file: it is skipped when it is as old as the object or older, and fetched when it is newer.

Worked cases. Each follows from the facts it cites; none was run against a bucket for this page (§13).

The download set the local file's time to the object's last-modified time (H1 example 3: "the last modified time of the local file is changed to the last modified time of the S3 object"). §8

The help text's two download rules

factkindsource
Example 3 of the installed help: "An S3 object will require downloading if the size of the S3 object differs from the size of the local file, the last modified time of the S3 object is newer than the last modified time of the local file, or the S3 object does not exist in the local directory."documentedH1 · Example 3
The same help, under --exact-timestamps: "The default behavior is to ignore same-sized items unless the local version is newer than the S3 version."documentedH1 · --exact-timestamps
The source follows the second: on a download, compare_time returns "no transfer" when the local file is as old as the object or older (§6). Example 3's "the S3 object is newer" does not trigger a download of a same-sized file at 2.39.2.documentedC1 · compare_time
Read the flag, not the example. Anyone relying on Example 3 to keep a local mirror current will keep a stale copy of every object rewritten at the same size. Use --exact-timestamps for a mirror pulled from S3.

§9

Transfer settings

The aws s3 transfer commands (cp, sync, mv, rm) share these, set under the s3 key of a profile in ~/.aws/config or with aws configure set default.s3.NAME VALUE. They change how fast and how hard the transfer stage works, never which files the decision picks.

§10

Exit codes

factkindsource
0 when every task succeeded with no warning; 1 when any task failed; 2 when none failed and any warned: if files[0].num_tasks_failed > 0: rc = 1, elif files[0].num_tasks_warned > 0: rc = 2.documentedC4 · run
The warnings of §3 (an unreadable or special file, an undecodable name, an invalid timestamp) and a Glacier object that cannot be transferred set 2; --ignore-glacier-warnings stops the Glacier warnings from doing so. A script that treats anything but 0 as failure fails a sync that skipped one unreadable file.documentedC5; H1 · --ignore-glacier-warnings

§11

Relationships

  • aws s3 cp --recursive runs the same listing, filters, and transfer stage without the comparator, so it transfers every listed file (§2). It is the tool when the decision rule would skip a file that must go.
  • aws s3 mv and aws s3 rm share the filters (§4) and the transfer settings (§9).
  • aws s3api is the low-level command set, one API call per command; it has no sync and no decision rule.
  • S3 itself. The rule rests on an object's LastModified and Size as the listing returns them; what sets LastModified is S3's, not the CLI's, and a later page on S3 objects is where it belongs (§13).

§13

Gaps and unverified claims

  • How a local file's size and time are read (get_file_stat in utils.py) was not read; whether the time is the modification time to the microsecond is assumed from §6, not confirmed.
  • The S3 listing's order and paging (BucketLister in utils.py) were not read; the shared order of §3 rests on the comparator's docstring (§3, unverified row).
  • How a download sets the local file's time is taken from the help's Example 3 sentence, not from the transfer code.
  • What sets an object's LastModified (the time of the write, not the uploaded file's time) is S3's behaviour and is not cited on this page; the upload cases of §7 assume it.
  • The strategy behind --no-overwrite and the CaseConflictSync class were not read; their rows rest on the help text.
  • Whether the transfer stage orders deletes after transfers, and how it retries, was not read (§7).
  • Glacier handling (--force-glacier-transfer, which objects warn) lives outside the files read.
  • How --checksum-mode and --checksum-algorithm act during a sync: they verify or set a checksum on the transfer, but they do not enter the decision (§6); the transfer side is not on this page.
  • Behavioural differences between the classic and crt clients during a sync beyond H3's list.
