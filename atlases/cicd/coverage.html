Code coverage reports

A code coverage report is the measurement of which code a test run executed, kept as a file: per source file, the lines, branches, statements, or functions that ran, and their totals as percentages. This page records its definition, the pipeline stage where it is made, the NIST, STIG, Department of Defense, and other federal documents that speak of it, and what the portfolio produces. A coverage report is evidence toward a control, and each control also requires a process; §3 to §5 state whose mapping each is.

§1

What a code coverage report is

factkindsource
SP 800-53's one description of code coverage, in the discussion of dynamic code analysis: organizations "may also consider conducting code coverage analysis (i.e., checking the degree to which the code has been tested using metrics such as percent of subroutines tested or percent of program statements called during execution of the test suite)".documentedS2 · SA-11(8)
The DoD tool category. "Test coverage tool": features "Measures how much code is exercised while the automated tests are running"; benefits "Shows the fidelity of the test results"; inputs "Application code, Automated tests"; outputs "The percentage of code that is exercised by the tests."documentedD7 · Table 14
DISA's wording: "Code coverage statistics describes the overall functionality provided by the application and how much of the source code has been tested during the release cycle." And: "Application developers should keep statistics that show all of the modules of the application and identify which modules were tested and when."documentedT1 · V-222649
The ESF guide: "Test coverage should identify the percentage of code paths the test plan covers as well as the types of test tools used."documentedG1 · §2.1, p. 7
What the report holds, from the portfolio's tools: SimpleCov's result set with line and branch counts (clubstraylight.com); JaCoCo's report directory, whose XML carries "LINE" and "BRANCH" counters of "missed" and "covered" (springboard backend); karma-coverage (Istanbul) output as HTML, lcov.info, and coverage-summary.json with statements, branches, functions, and lines (springboard frontend). Details and commits in §8.portfoliospringboard · scripts/pr-summary.mjs, src/main/frontend/karma.conf.js · b2fdcb9
Three other senses of "coverage". The documents use the word for other measures, and the controls of §3 mostly mean these. SA-11: "The coverage of testing and evaluation refers to the scope (i.e., number and type) of the artifacts included in the assessment process." SA-11(7): testing that "provides complete coverage of the required controls". RA-5(3): "the breadth and depth of vulnerability scanning coverage". SP 800-53A gives coverage as an assessment attribute with the values "basic, focused, and comprehensive". Only the SA-11(8) passage, the STIG rule, the DoD tool row, and the ESF and SP 800-204D sentences mean code coverage (S2; S6 · App. C).

§7

Limits stated in the sources

factkindsource
Full coverage is not required of large applications: "Some applications are so large that it is not feasible to test every last bit of the application code on one release cycle. In those instances, it is acceptable to prioritize and identify the modules that are critical to the applications security posture and test those first." And: "If the application is smaller in nature and all aspects of the application can be tested, the code coverage statistics would be 100%."documentedT1 · V-222649
In SP 800-53 coverage analysis is optional and supporting: organizations "may also consider" it "To understand the scope of dynamic code analysis and the assurance provided".documentedS2 · SA-11(8)
The DoD tool row gives the benefit as "Shows the fidelity of the test results": a statement about the tests, not about the code's security.documentedD7 · Table 14
The ESF's baseline is hedged: "Baseline levels of code coverage should ideally be achieved".documentedG1 · §2.1
SP 800-53A leaves the extent to the organization, which "provides direction on the type, number, and specific objects to be tested".documentedS6 · App. C, fn. 57

§9

Relationships

  • Test results (test-results.html). The same test run produces both. In clubstraylight.com they share one artifact, test-results; springboard uploads them separately (surefire-reports beside the two coverage artifacts). Shared control: SA-11. STIG: V-222644 for results, V-222649 for coverage.
  • Static analysis (static-analysis.html). SP 800-204D puts SAST, DAST, and coverage reports in one sentence (§2). Shared control family: SA-11, with SA-11(1) for static and SA-11(8) for dynamic analysis.
  • Vulnerability scan (vulnerability-scan.html). RA-5(3) and STIG V-222515 use "coverage" for scanning; NIST's 1.2 draft maps PW.8.2 to RA-05 and RA-05(03).
  • Evidence manifest (evidence-manifest.html) and attestation (attestation.html). springboard's manifest checks and classes the coverage directories; both repositories' attest zips take files from the merged artifact directory (§8).
  • OSCAL (oscal.html). springboard's SSP fragment cites coverage reports under sa-11. Audit events (audit-events.html): springboard's test job emits audit-event-test.json.
  • SBOM (sbom.html). No control is NIST-mapped to both in SSDF 1.1. In the 1.2 draft, PW.8.2 adds RA-05 and SI-02, which the SBOM page's §6 lists as its own reading for the SBOM.
