Static analysis and lint results

Static analysis and lint results are the findings a linter or static analyzer reports on source code that is not running, kept as the record of one run: the tool, its configuration, the commit, each finding, and the outcome. This page records the definitions, the pipeline stages where the findings are made, and the NIST, STIG, Department of Defense, and other federal documents that ask for them or read them, then what the portfolio's pipelines keep. A findings file is evidence toward a control, and each control also requires a process; §3 states whose mapping each control is.

§1

What static analysis and lint results are

factkindsource
The SSDF separates two kinds of review of human-readable code: "code review (a person looks directly at the code to find issues)" and "code analysis (tools are used to find issues in code, either in a fully automated way or in conjunction with a person)". "Human-readable code includes source code, scripts, and any other form of code that an organization deems human-readable."documentedS1 · PW.7, PW.7.1
SP 800-53's enhancement for the analysis: "Require the developer of the system, system component, or system service to employ static code analysis tools to identify common flaws and document the results of the analysis." Its discussion: "Static code analysis provides a technology and methodology for security reviews and includes checking for weaknesses in the code as well as for the incorporation of libraries or other included code with known vulnerabilities or that are out-of-date and not supported."documentedS2 · SA-11(1)
The DoD tools table defines the SAST tool: "SAST analyzes application static codes, such as source code, byte code, binary code, while they are in a non-running state to detect the conditions that indicate code weaknesses." Its inputs are "Source code; Known vulnerabilities and weaknesses"; its output is "Static code scan report and recommended mitigation."documentedD7 · Table 14
The same table defines the lint tool: it "Analyzes source code to flag programming errors, bugs, stylistic errors, and suspicious constructs. Applicable to both compiled or interpreted languages". The tables spreadsheet gives its benefits as "Improve code readability; Pre-code review; Finding (syntax) errors before execution for interpreted languages" and its output as "Analyze results".documentedD7 · Table 14; D8 · Tools sheet
SP 800-204D treats the findings as a build artifact: "An artifact is the result or outcome of a CI process." "If the step involves running a SAST tool on the same source code, the artifact will be the “Scan Result.”" An attestation over it "falls under the category of artifacts attestation."documentedS4 · §5.1.1
What the record holds, from SP 800-53: "Evidence of the correct implementation of static analysis can include aggregate defect density for critical defect types, evidence that defects were inspected by developers or security professionals, and evidence that defects were remediated."documentedS2 · SA-11(1)
What the record holds, from the SSDF: the issues found are recorded and triaged "in the development team’s workflow or issue tracking system" (PW.7.2), and the tool configuration is a documented item: "Documents the specific tool options and tool configurations used in the development process" (SA-15 a.3).documentedS1 · PW.7.2; S2 · SA-15
A run record. Read together, the sources ask a findings file to carry the tool and its configuration, the code it was run on, the findings, and what was done with them. A record that ties these to one commit lets a reader say which code a finding was about. That combination is this page's reading; no one source lists it.

Where in a pipeline they are made

The DoD Activities & Tools Guidebook places static analysis in four of its phase tables. Each step gives the activity, its baseline, and its output, verbatim (D7; SSDF columns cross-checked against the tables spreadsheet, D8).

1Develop"Static code scan before commit", REQUIRED, SSDF "PW.7.1, PW.7.2": "Scan and analyze the code as the developer writes it. Notify developers of potential code weakness and suggest remediation." Output "source code weakness findings"; tool "IDE security plugins". Also "Static analysis", REQUIRED: "Static code analysis examines code to identify issues within the logic and techniques." Output "Static code analysis report" (Table 5).
2Build"Compile and link", tools "Build tool; Lint tool; Artifact repository" (Table 6). "Static application security test and scan", REQUIRED: "Perform SAST to the software system". Output "Static code scan report and recommended mitigation." (Table 6).
3Build record"Build configuration control and audit", REQUIRED, SSDF "PS 3.2": "Track build results, SAST and dependency checking report". Inputs "Build results; SAST report; Dependency checking report"; outputs "Version controlled build report; Action items; Go/no-go decision" (Table 6).
4Test"Static application security test (SAST) and scan", REQUIRED, SSDF "RV.1.2, RV.2.1, RV.3.1, RV.3.2, RV.3.3": "Perform Static Application Security Tests (SAST) on the software system." Output "Static code scan report and recommended mitigation" (Table 7).

NIST: the SSDF tasks and the SP 800-53 controls

Each control below also requires a process (a plan, a frequency, remediation, review), so a findings file is evidence toward the control and does not meet it alone. The first table is NIST's mapping, from the SSDF's reference column. The second quotes the control text; its "basis" column marks the rows that are this page's reading.

§7

Limits stated in the sources

factkindsource
False positives: "A high density of ignored findings, commonly referred to as false positives, indicates a potential problem with the analysis process or the analysis tool. In such cases, organizations weigh the validity of the evidence against evidence from other sources."documentedS2 · SA-11(1)
Context: manual reviews find weaknesses that "require knowledge of the application’s requirements or context that, in most cases, is unavailable to automated analytic tools and techniques, such as static and dynamic analysis."documentedS2 · SA-11(4)
Language: "static analyzers work better on statically-typed languages such as C++, since the type of variables used within the code are known at compile time, whereas dynamically-typed languages such as Python resolve the variable types at runtime." And: "The complexity and thoroughness of these static scanning technologies vary greatly."documentedG2 · p. 16
Completeness: "No automated security scanning tool is perfect, so it is important to manually review the code and the CI/CD pipeline."documentedG1 · p. 13
The STIG, of static analysis run with tests for error handling: "These tests may give indications of vulnerability, but they are not comprehensive."documentedT1 · V-222656
Scope of a lint tool, from the DoD build phase: "lint tools help to check for some potential errors such as syntax errors."documentedD7 · §3.4
Bypass: among the risks in an SSC, "Checks, such as scanning and various types of tests (e.g., static, dynamic, or interactive), may have been bypassed in the CI/CD process."documentedS4 · §3.1.5

§9

Relationships

  • Vulnerability scan (vulnerability-scan.html). SCA reads dependencies; static analysis reads the code written in the repository. The DoD Guidebook keeps them as separate activities with separate reports (§2, step 3). springboard's job "Vulnerability Scan (PW.7 / PW.8)" runs npm audit and Trivy, and the golden-pipeline skill maps PW.7 to npm audit (§8). RA-5 and SA-15(7) are shared controls.
  • Secrets scan (secrets-scan.html). The ESF guide counts secret detection as static analysis: "Performing static analysis to scan for secrets before commit and during CI/CD blocks secrets from the code base" (G2 · p. 16).
  • Test results and coverage (test-results.html, coverage.html). SA-11 is shared: its part c asks for "the results of the testing and evaluation", and SSDF PW.8 maps there as PW.7 does. SP 800-204D §5.1.4 asks for SAST with "code coverage reports". STIG V-222648 and V-222649 both cite CCIs mapped to SA-11 (4).
  • Audit events (audit-events.html). springboard's Checkstyle job keeps only its audit event.
  • Evidence manifest and attestation (evidence-manifest.html, attestation.html). slacronym's lint file is hashed in the attested zip; springboard's manifest lists no lint file.
  • Provenance (provenance.html). SP 800-204D files a SAST "Scan Result" under artifacts attestation, one of four attestation kinds beside environment, process, and materials.
  • OSCAL (oscal.html). springboard's scripts/generate-oscal.js lists SA-11 among reviewed controls and describes its implementation as "automated tests (JUnit, Karma, Playwright)"; the lint jobs are not part of that description (springboard · scripts/generate-oscal.js · b2fdcb9).
  • SBOM (sbom.html). The SBOM page's DoD section quotes the same cATO requirement SA04, "dependency analysis, static and dynamic application analysis" (sbom.html §8). SA-11(1)'s discussion includes checking "for the incorporation of libraries or other included code with known vulnerabilities", which overlaps the component list an SBOM supplies.

  • In SSDF 1.1, PW.5.1, whose Example 7 is linters and formatters, carries no SP 800-53 reference; the 1.2 draft gives it SA-15, SI-03, SI-10, SI-10(03) (2026-11-14).
  • springboard's Checkstyle execution is bound to the Maven validate phase, so ./mvnw -B -ntp verify in the test job runs it as well as the checkstyle job (pom.xml, golden-pipeline.yml at b2fdcb9; 2026-11-14).
  • Of the eleven jobs in springboard's golden-pipeline.yml, four carry an SSDF or OMB label in their display name: "Secrets Scan (PW.6)", "Vulnerability Scan (PW.7 / PW.8)", "SBOM (PW.4)", "OSCAL (M-24-15)". The two static analysis jobs carry none (2026-11-14).
  • The versions of ESLint and Prettier in §8 are the ranges in package.json; the installed versions are fixed by the lockfiles (npm ci, yarn install --immutable), which were not read.
  • The pdftotext extraction of SP 800-53A drops the "ti" ligature ("acquision"); the quotations in §3 restore it. The extraction of the DoD Guidebook interleaves table columns; its SSDF columns in §2 were checked against the tables spreadsheet rows.
