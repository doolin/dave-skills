Evidence manifest and retention classes

An evidence manifest is the hashed inventory of the evidence files one pipeline run produced: a path, a size, and a SHA-256 digest per file, with a class for each file and the retention class it is assigned. In the portfolio it is evidence-manifest.json, written by springboard's verify-evidence job, which also copies the pipeline definition into the evidence set. This page records what the issuing documents say about archiving and protecting such evidence (NIST, STIG, DoD), and checks each NARA General Records Schedule citation in the script against the schedule text (§6). None of the three citations fits all the evidence assigned to it: GRS 5.1 and GRS 2.7 cover other records and set no permanent or 90-day disposition, and GRS 3.2 covers the scans but gives no 3-to-7-year period.

§1

What an evidence manifest is

No issuing document read for this page defines an "evidence manifest"; "manifest" was searched in SP 800-218 (both versions), SP 800-204D, the DoD cATO documents, and the ESF developers' guide, and occurs only in the DoD tables as infrastructure "manifests". The SSDF defines the two words the artifact is built from.

factkindsource
"An artifact is "a piece of evidence" [adapted from IR7692]. Evidence is "grounds for belief or disbelief; data on which to base proof or to establish truth or falsehood" [SP800160]. Artifacts provide records of secure software development practices." The 1.2 draft carries the same footnote, citing "[IR7692]" without "adapted from", and its change list records "Added definitions of "provenance," "artifact," and "evidence"".documentedS1 · PO.3.3 n. 6; S5 · PO.3.3 n. 6
What the portfolio's pattern asks of the manifest: "At minimum, each entry must include: path, size, sha256, and artifact-class". "The manifest should also carry per-artifact retention-class metadata binding each artifact to its expected GRS item and minimum retention period, so that downstream archival can enforce retention without external lookup."portfoliodave-skills · skills/cicd-golden-pipeline/SKILL.md · 96d1f33
What springboard's manifest holds: generated_at, commit, run_id, repo; artifacts, one entry per file under evidence/ with path, size, sha256, artifact-class, retention-class; and the expected, missing, expectedDirs, missingDirs lists. The retention class is one word; no entry carries a GRS item or a period.portfoliospringboard · scripts/verify-evidence.js · b2fdcb9
The script's own statement of purpose: "Fails the job if any expected artifact is missing — this is the drift-detection step that catches silent upstream breakage."portfoliospringboard · scripts/verify-evidence.js lines 3–4 · b2fdcb9

§2

Where in a pipeline it is made

After every evidence-producing job and before packaging or archival. The sources describe the evidence trail and its storage; none describes a manifest step by itself.

factkindsource
A build is wrapped "with capabilities to gather evidence and ultimately create an evidence trail of the entire SDLC". "The second type of evidence that should be gathered consists of the hash of the final build artifact, files, libraries, and other materials used in the artifacts and all events. This is then signed by a trusted component of the build framework that is not under the control of the developers".documentedS4 · §5.1.1
"In the context of "concurrent generation of evidence," the evidence generated should be enabled by a process with a higher level of trust or isolation than the build itself to protect against tampering."documentedS4 · §5.1.1
Storage: "The attestations must be cryptographically signed using a secure key." "The storage location must be tamper-proof and protected using robust access control."documentedS4 · §5.1.1
For a release: "GitOps-REQ-2: Package managers that facilitate GitOps should preserve all data on the packages that were released, including the version numbers of all modules, all associated configuration files, and other metadata as appropriate for the software operational environment." 800-204D's mapping table files §5.2.1 under SSDF PS.3, "Archive and Protect Each Software Release".documentedS4 · §5.2.1, Table
