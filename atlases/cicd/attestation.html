Atlases · CI/CD · attestation

Attestation report and evidence archive

The portfolio's record of a pipeline run: every CI artifact of the run zipped into one bundle, the bundle's SHA-256 posted in a Solana Memo transaction, a PDF and a JSON report of the run, and the bundle, its files, and the report copied to an S3 compliance bucket through an OIDC role. clubstraylight.com, springboard, and slacronym each make one. The word "attestation" carries three meanings in the sources, and this page keeps them apart (§1): this run record; the SLSA and in-toto build attestation (provenance.html); and the software producer's self-attestation to the federal government (§6). The record is evidence toward the controls of §3; each control also requires a process, and each mapping states whose it is.

§1

What the run record is, and the three senses of "attestation"

No issuing body defines this record; the portfolio's skill does. The PDF it renders carries the heading "CI/CD Pipeline Attestation". The nearest issuing-body term is the SSDF's "artifact".

factkindsource
The pattern's own description: it "Zips CI artifacts, SHA-256s the archive, posts the hash as a JSON memo on Solana, generates a PDF attestation report plus the same content as queryable attestation.json, and uploads everything to S3." Its stated purpose: "Create a tamper-proof, on-chain record that a CI/CD pipeline ran for a specific commit and what it produced."portfoliodave-skills · skills/solana-cicd-hash/SKILL.md · 96d1f33
What the JSON record holds, per the skill: schema_version, repository, commit_sha, branch, ci_run_url, origin (ci or local), s3_key, artifact_checksum, included_files, solana_network, solana_tx_signature, solana_error, completed_at, steps. "It records what was attested, not whether the checks passed: pass/fail lives in each tool's own output file."portfoliodave-skills · skills/solana-cicd-hash/SKILL.md · 96d1f33
The memo is posted to the Memo program, which "validates a string of UTF-8 encoded characters and verifies that any accounts provided are signers of the transaction. The program also logs the memo, as well as any verified signer addresses, to the transaction log". Its log lines begin "Program MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr invoke [1]".documentedW1 · Memo, Logs
The SSDF's term for such a record: "An artifact is “a piece of evidence” [adapted from IR7692]. Evidence is “grounds for belief or disbelief; data on which to base proof or to establish truth or falsehood” [SP800160]. Artifacts provide records of secure software development practices."documentedS1 · p. 7, note 6

The three are different things made by different parties for different readers. This page covers the first; the second is provenance.html; the third is §6.

Where the senses meet. A run record can serve as one of the "artifacts that demonstrate conformance" that EO 14028 sec. 4(e)(ii) and M-22-18 let a purchaser request in support of a self-attestation (§6). It is neither an in-toto attestation nor a self-attestation: its files are not signed, and the one signature in it is the Solana transaction's, made with a key the pipeline holds (§10). This is this page's reading.

§2

Where in a pipeline it is made

The run record is the last job of a pipeline run. The steps below are the clubstraylight.com attest job; §8 gives where the other two differ.

1Checks uploadEach check job uploads its output as a GitHub Actions artifact, kept 90 days.
2DownloadThe attest job, after every check job passes and on pushes to the main branch only, downloads all of the run's artifacts into ci-artifacts/ with merge-multiple: true.
3Zip and hashThe script zips every regular file at the top of that directory into ci-artifacts.zip and takes the zip's SHA-256.
4AnchorIt posts a JSON memo with the S3 key, the checksum, the commit, a timestamp, the network, and the origin to Solana devnet, signed by the keypair from the SOLANA_KEYPAIR secret.
5ReportIt writes attestation.json (one line) and attestation.pdf from the same evidence object.
6ArchiveWith an OIDC role assumed, it copies each artifact file, the zip, the PDF, and the JSON to s3://<bucket>/<prefix>/YYYY/MM/DD/HHMMSS-<sha7>/.
7TagA shell step tags the SBOM object in S3 with its SSDF task and SP 800-53 controls.
8KeepThe zip, PDF, and JSON are uploaded as the attestation artifact, 90 days, and the keypair file is removed.

§6

Other federal documents: the producer's self-attestation

The third sense of the word. A company officer signs a statement that the company's development practices conform to SSDF-derived requirements; a federal agency collects it. It was required by M-22-18 from 2022 and is optional since M-26-05 of 2026-01-23.

whenfactkindsource

What the run record could be in this regime. Under M-22-18 or a form adopted under M-26-05, the run record is the kind of thing an agency "may obtain" as an artifact, or that a producer attaches to the form. It cannot stand in for the form, which is a signed statement of practices by a person with "the authority to bind the corporation" (C1 · p. 4). This is this page's reading.

§9

Relationships

  • Build provenance (provenance.html). springboard's package job runs actions/attest-build-provenance v4.1.0 on the jar: an in-toto attestation of the release, signed through GitHub. The run record covers the run's evidence, not the jar. Both map to SR-4.
  • RFC 3161 timestamp (timestamp.html). springboard requests one for the same digest the memo carries, so the bundle has two time anchors.
  • Evidence manifest (evidence-manifest.html). springboard's verify-evidence job hashes each file and fails on a missing one; the run record hashes the zip as a whole and fails only when no file is found. The manifest is one of the zip's inputs.
  • SBOM (sbom.html, §6 there). The SBOM is inside the bundle; clubstraylight.com tags its S3 object with PS.3.2's controls. PS.3.2 and SR-4 are shared.
  • Audit events (audit-events.html). springboard's attest job echoes an audit event line after it runs. AU-9 and AU-11 are shared.
  • OSCAL (oscal.html). springboard's OSCAL files are among the bundle's inputs.
  • Test results, coverage, scans (test-results.html, coverage.html, vulnerability-scan.html, secrets-scan.html, static-analysis.html). These are the files the bundle holds; the run record is their archive.

§10

Observed

  • The checksum is of the zip's bytes. Verification compares the archived zip; a zip rebuilt from the same files is not expected to match, since the archive carries its own entry headers (reading of the scripts, not tested; 2026-11-14).
  • The PDF and the JSON record are written after the checksum and are outside the zip, so the memo's hash does not cover them. The skill gives the reason for the JSON: it "carries the zip's checksum" (2026-11-14).
  • The one signature in the record is the Solana transaction's. The key is a repository secret, and per CSL-0227 the same keypair (dbb's) signs for more than one repository, so the signer address identifies the key, not the repository; the memo's s3_key does that (2026-11-14).
  • springboard writes attestation.json after its S3 step, so the bucket never receives it; its tsaTimestamp is the runner's clock at verification, not the time in the TSA's response (reading of scripts/attest.mjs at b2fdcb9, 2026-11-14).
  • springboard's attest and package jobs both need only compliance, so whether the app-jar artifact is among the downloaded files depends on which finishes first (reading of the workflow; not checked against a run).
  • slacronym's PDF says the archive and the attestation "were uploaded to S3" and is rendered before the upload step runs. Its attest steps run on pull requests, where the memo's commit is GITHUB_SHA, the merge commit; the PR head is in run-record.json as head_sha only (2026-11-14).
  • springboard's notes label GRS 3.1/040 "IT ops + maintenance". The GRS 3.1 copy read here (Transmittal 30) gives item 020 as "Information technology operations and maintenance records" and item 040 as "Information technology oversight and compliance records" (2026-11-14).
  • EO 14306 sec. 1(a) redesignates EO 14144's 2(c)–(e) as 2(a)–(c) before sec. 2(b) replaces "subsection 2(c)"; the inserted text matches the content of EO 14144's original 2(c) (2026-11-14).
  • Searched for "attest" with no occurrence: EO 14306, the NSA/CISA CI/CD guide, and the DoD documents listed in §5 (2026-11-14).
