Build provenance and artifact digests

Build provenance is a signed statement, made by the build platform, of how an artifact was built: the platform, the build process, its inputs, and the cryptographic digest of each output. In SLSA it is an in-toto attestation with the predicate type https://slsa.dev/provenance/v1. The artifact digest is the hash of the release file itself, which a recipient recomputes and compares. This page records the definitions, the pipeline stage where both are made, the NIST, STIG, Department of Defense, and other federal documents that ask for them, and the portfolio's use. Provenance describes one build. The portfolio's attestation report (attestation.html) records the evidence of one pipeline run and anchors its hash on Solana; the trusted timestamp is timestamp.html.

§1

What build provenance and an artifact digest are

factkindsource
SLSA: "It’s the verifiable information about software artifacts describing where, when, and how something was produced." Its purpose: "Describe how an artifact or set of artifacts was produced so that: Consumers of the provenance can verify that the artifact was built according to expectations. Others can rebuild the artifact, if desired."documentedL1 · Purpose
The model: "Provenance is an attestation that a particular build platform produced a set of software artifacts through execution of the buildDefinition." The build track summary: "Provenance describes what entity built the artifact, what process they used, and what the inputs were."documentedL1 · Model; L2 · Build track
The digest is required at every level: "The build process MUST generate provenance that unambiguously identifies the output package by cryptographic digest and describes how that package was produced."documentedL3 · Provenance Exists
The container is an in-toto attestation: "An in-toto attestation is authenticated metadata about one or more software artifacts". It has four layers: Predicate ("arbitrary metadata about a subject artifact, with a type-specific schema"), Statement ("Binds the attestation to a particular subject and unambiguously identifies the types of the predicate"), Envelope ("Handles authentication and serialization"), and Bundle ("a method of grouping multiple attestations together").documentedI1 · spec
The Statement's subject is the "Set of software artifacts that the attestation applies to. Each element represents a single software artifact. Each element MUST have digest set." "Subjects are assumed to be immutable, i.e. the artifacts identified by the subject SHOULD NOT change." Its _type is "Always https://in-toto.io/Statement/v1 for this version of the spec."documentedI2 · Fields
The SP 800-53 definition, which the SSDF 1.2 draft adopts in a footnote: provenance is "the chronology of the origin, development, ownership, location, and changes to a system or system component and associated data. It may also include personnel and processes used to interact with or make modifications to the system, component, or associated data".documentedS7 · SR-4; S5 · note 5
The digest of a release file, without provenance, is the SSDF's first example under PS.2.1: "Post cryptographic hashes for release files on a well-secured website." The STIG: "application files and/or application packages are cryptographically hashed using a strong hashing algorithm. Comparing hashes after transferring the files makes it possible to detect changes in files".documentedS1 · PS.2.1; T1 · V-222645
The SSDF's word for both: "An artifact is “a piece of evidence” [adapted from IR7692]." "Artifacts provide records of secure software development practices."documentedS1 · note 6

The SLSA Build levels

The level table, verbatim (L2 · Levels and tracks).

levelrequirementsfocussummary, verbatim

Build L1"Provenance showing how the package was built""Mistakes, documentation""Package has provenance showing how it was built. Can be used to prevent mistakes but is trivial to bypass or forge."
Build L2"Signed provenance, generated by a hosted build platform""Tampering after the build""In practice, this means that builds run on a hosted platform that generates and signs the provenance." The consumer must "Validate the authenticity of the provenance."

Three uses of "attestation". In SLSA and in-toto an attestation is signed metadata about an artifact, and provenance is one kind. In EO 14028 sec. 4(e)(ix) and the CISA form, an attestation is a software producer's signed statement that it follows secure development practices (§6). In the portfolio, the attestation report is the record of one pipeline run's evidence: a zip of the run's artifacts, its SHA-256, and a Solana memo carrying that hash (attestation.html). The three are separate artifacts.

§2

Where in a pipeline they are made

Both are made at the end of the build, on the build platform, before the artifact is stored or delivered. SP 800-204D lists four components of a build attestation (S4 · §5.1.1, verbatim):

1Environment"Environment attestation involves an inventory of the system when the CI process happens and generally refers to the platform on which the build process is run."
2Process"Process attestation pertains to the computer programs that transformed the original source code or materials into an artifact (e.g., compilers, packaging tools) and/or the programs that performed testing on that software".
3Materials"Materials attestation pertains to any raw data and can include configuration, source code, and other data (e.g., dependencies)."
4Artifacts"An artifact is the result or outcome of a CI process." "An attestation pertaining to this newly generated product falls under the category of artifacts attestation."
factkindsource
Secure build requires to "Ensure the concurrent generation of evidence for build attestation to demonstrate compliance with secure build processes during the time of software delivery." The evidence "consists of the hash of the final build artifact, files, libraries, and other materials used in the artifacts and all events. This is then signed by a trusted component of the build framework that is not under the control of the developers using a digital certificate to create the attestation".documentedS4 · §5.1.1, p. 16
The signer sits above the build: "the evidence generated should be enabled by a process with a higher level of trust or isolation than the build itself to protect against tampering." Storage: "The attestations must be cryptographically signed using a secure key." "The storage location must be tamper-proof and protected using robust access control."documentedS4 · §5.1.1, p. 17
Use at deployment. "DEPLOY-REQ-3: If a secure build environment and associated process have been established, it should be possible to specify that the artifact (i.e., container image) being deployed must have been generated by that build process in order to be cleared for deployment."documentedS4 · §5.2
Between steps: "The inputs and outputs of each build step should be verified to ensure that the correct steps have been executed by the expected component or entity." Table 1's note: "The addition of attestations like VSA does not necessarily imply that the artifact manager is trusted."documentedS4 · §4.2
SLSA's build model: "Each build runs as an independent process on a multi-tenant build platform." "Finally, the build process outputs one or more artifacts, identified by subject." At Build L1 the platform must "Automatically generate provenance describing how the artifact was built"; the producer must "Distribute provenance to consumers".documentedL1 · Model; L2 · Build L1; L3 · Distribute provenance
The DoD guidebook places the checksum and signature in the Build phase. Table 6, row "Release packaging", baseline REQUIRED, SSDF PS.2.1, PS.3.1, PS.3.2: "Package binary artifacts, VM images, infrastructure configuration scripts, proper test scripts, documentation, checksum, digital signatures, and release notes as a package." Output: "Released package with checksum and digital signature". Tool: "Release packaging tool".documentedD4 · Table 6, p. 22
ESF: "The package including the correct metadata should be signed by a cryptographically-secure signature algorithm before being uploaded to the repository. Alternatively, the package can include cryptographic hashes. The package manager should verify the signature or hashes and the metadata including the version number."documentedN2 · p. 35
ESF on what a build's artifacts are: "The artifacts for builds should include, at a minimum, the source repository, the third-party dependencies, the build script, and the output of the build." "All artifacts should be retained by the supplier for the entire support lifetime of the product until it is marked for end of life." The mitigations "can be modeled after the emerging frameworks, including build requirements of the Supply-Chain Levels for Software Artifacts (SLSA) project".documentedN2 · p. 32
NSA and CISA: "NSA and CISA recommend implementing secure code signing to establish digital trust within the CI/CD pipeline. Ensure code is continuously and properly signed and that the signature is verified throughout the CI/CD process, regardless of the stage of development."documentedN1 · pp. 10–11
On GitHub Actions the provenance is made by a workflow step placed "After the step where the binary has been built", with the permissions id-token: write, contents: read, attestations: write. The step on GitHub's page is actions/attest@v4 with subject-path. Verification: gh attestation verify PATH/TO/YOUR/BUILD/ARTIFACT-BINARY -R ORGANIZATION_NAME/REPOSITORY_NAME.documentedG1 · binaries; verifying

Fields the build itself may write at L2: "The names and cryptographic digests of the output artifacts, i.e. subject in SLSA Provenance", and "Any field that is not marked as REQUIRED for Build L2." Dependency completeness is "best effort".documentedL3 · Provenance is Authentic
Verification depends on the consumer's expectations: "Consumers MUST accept only specific signer-builder pairs."documentedL1 · Builder
"IMPORTANT: Subject artifacts are matched purely by digest, regardless of content type."documentedI2 · subject
SP 800-204D: "no recommendations were provided with respect to the specific artifacts and frameworks associated with SSC security, such as SBOMs, code signing, and attestation." The process attestation "should be considered “best effort.”"documentedS4 · §6, §5.1.1
A signature is as good as the signer: "if the signing facility itself has been compromised, then the delivered artifact may also have been compromised, and the signature validates the compromised artifact and not the true artifact." NSA and CISA: "If a code signing identity itself is compromised, it undermines trust."documentedN2 · p. 33; N1 · p. 11
Services: "Software delivered to a customer as a service rather than as a binary artifact will not typically be delivered with a cryptographic signature."documentedN2 · p. 33
The STIG excuses vendors: "If the application being reviewed is a COTS product and the vendor did not provide a hash value for validating the package, this is not a finding."documentedT1 · V-222645
GitHub: "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, artifact attestations are only available for public repositories. To use artifact attestations in private or internal repositories, you must be on a GitHub Enterprise Cloud plan."documentedG1 · Who can use this feature?

§9

Relationships

  • Attestation report (attestation.html). SLSA provenance describes one build of one artifact and is signed through the build platform. The portfolio's attestation records the evidence of one pipeline run (test, scan, SBOM, and other files), hashes the zip of it, and anchors that hash in a Solana memo. They share SHA-256 and the word "attestation", nothing else (§1).
  • Trusted timestamp (timestamp.html). springboard's attest job requests an RFC 3161 token over the evidence zip's digest. SLSA's requirements recommend "time stamping services" where a transparency log is not appropriate, for detecting key compromise (L3 · Provenance is Authentic).
  • SBOM (sbom.html). The SBOM lists what a release contains; provenance says how it was built. The SSDF files both under PS.3.2, and the two pages share SR-3 and SR-4 (sbom.html §6). GitHub's attest action also signs SBOM attestations through sbom-path; no portfolio workflow uses it (G1).
  • Evidence manifest (evidence-manifest.html): where the jar's .sha256 would be listed if the evidence zip holds it (§10).
  • Vulnerability scan (vulnerability-scan.html). SP 800-204D's DEPLOY-REQ-4 asks that an image be "scanned for vulnerabilities and attested for vulnerability findings", a second predicate type on the same subject.
  • Test results (test-results.html). springboard's package job skips tests because they ran in the compliance job.
  • Audit events (audit-events.html): the package job's "event":"package" line.
  • OSCAL (oscal.html): SA-10(1), SR-4, and SI-7(6) are the controls an assessment result would cite for this artifact.

§10

Observed

  • The three SLSA v1.1 pages fetched carry "Status: Retired" and "Version 1.2 is the current version." This page quotes v1.1 (2026-11-14).
  • GitHub's how-to page shows actions/attest@v4; springboard pins actions/attest-build-provenance v4.1.0. The page as read does not say how the two actions relate (2026-11-14).
  • In springboard, attest needs only compliance, so it runs alongside package. Whether app-jar and its .sha256 exist when attest downloads the run's artifacts depends on timing; if they do not, the jar's digest reaches neither the evidence zip nor the S3 archive and lives 90 days in app-jar and in GitHub's attestation store. The shared skill's needs: [compliance, deploy] would order them. This is a reading of the workflow file; no run log was read (2026-11-14).
  • springboard writes built_at, a wall-clock time, into version.json inside the jar before packaging, so two builds of one commit yield different digests. This bears on SSDF PO.3.2 Example 4 (reproducible builds) and SLSA's purpose "Others can rebuild the artifact, if desired." (2026-11-14).
  • springboard's provenance step runs in the same job as ./mvnw. SLSA L3 requires that signing material be inaccessible "to the user-defined build steps". GitHub's page as read states no SLSA level for its attestations, so the level springboard reaches is not established here (2026-11-14).
  • The jar that is attested is a second Maven build of the commit, in the package job, not the build the compliance job tested (step name, ci-cd.yml, 2026-11-14).
  • SP 800-53A's extracted text drops the "ti" and "fi" ligatures ("Organizaonal"); the quotations in §3 restore the letters. SSDF 1.2's PS.2.1 references run across the page break between PDF pages 29 and 30; the mapping in §3 is read from both (2026-11-14).

§11

Gaps and unverified claims

  • SLSA v1.2, now current, was not read; differences from v1.1 are unknown here.
  • The SLSA Build level of GitHub artifact attestations, how GitHub signs them, and where it stores them: GitHub's "Artifact attestations" concepts page, linked from the how-to, was not read.
  • No springboard attestation was fetched or verified with gh attestation verify; its builder.id, buildType, and externalParameters are not recorded here.
  • springboard's repository visibility and GitHub plan, which decide whether attestations are available (§7), were not checked.
  • Whether the evidence zip of a springboard master run holds app-jar (§10); needs a run's artifact list.
  • The in-toto Envelope, Bundle, and ResourceDescriptor specifications were not read.
  • NIST's white paper Security Considerations for Code Signing, cited by SSDF 1.2 note 8 and by NSA/CISA, was not read.
  • SP 800-204D's reference [9], the source of its four attestation types, was not read.
  • The CCI references in §4 were not cross-checked against DISA's CCI list (U_CCI_List.zip); CCI-001749 carries no Rev. 5 reference in the STIG text.
  • NARA GRS 3.1 item 030, Configuration and change management records, lists "documentation of software distribution (including COTS software license management files) and release or version management"; its disposition did not extract in reading order and was not read (R1 · p. 6).
  • SSDF 1.2 is a draft; its mappings may change in the final.
