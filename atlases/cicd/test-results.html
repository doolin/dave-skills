Atlases · CI/CD · test results

Test results

Test results are the machine-readable record of a test run: which tests ran against which build, what each returned, and the tally. This page records what the issuing documents call the artifact, the pipeline stage where it is made, the NIST, STIG, and Department of Defense documents that ask for it or read it, and what the portfolio's pipelines write. A test result is evidence toward a control, and each control also requires a process; §3 to §5 state whose mapping each is. Coverage reports have their own page, coverage.

§1

What a test result is

None of the documents read defines "test results" as a term. They define the artifact it is a kind of, and say what a test activity puts out.

factkindsource
The SSDF's definition of the class: "An artifact is “a piece of evidence” [adapted from IR7692]. Evidence is “grounds for belief or disbelief; data on which to base proof or to establish truth or falsehood” [SP800160]. Artifacts provide records of secure software development practices."documentedS1 · PO.3.3, footnote 6
SA-11's statement asks for the artifact: the developer is to "Produce evidence of the execution of the assessment plan and the results of the testing and evaluation". The discussion says the assessment plans state "the types of artifacts produced during those processes", and that "The coverage of testing and evaluation refers to the scope (i.e., number and type) of the artifacts included in the assessment process."documentedS2 · SA-11c, discussion
The SSDF task: "Scope the testing, design the tests, perform the testing, and document the results, including recording and triaging all discovered issues and recommended remediations in the development team’s workflow or issue tracking system."documentedS1 · PW.8.2
What a unit test takes and gives, in the DoD activity table. Inputs: "Unit test script, individual software unit under test (a function, method or an interface), test input data, and expected output data". Output: "Test report to determine whether the individual software unit performs as designed."documentedD4 · Table 5, Unit test
The record kept of tests across phases: "Test audit keeps who performs what test at what time and test results in records". Its input is "Test activity and test results"; its output, "Test audit log".documentedD4 · Table 7, Test Audit
The build's outputs: "The outputs from continuous build process are build results, build reports (e.g., the unit test report, and a static code analysis report), and artifacts stored into Artifact Repository." Continuous integration adds "automation test results and security scan results."documentedD6 · Continuous Build, Continuous Integration
SP 800-204D states the integrity property and sets it aside: "providing support for artifact testing (that generates tamper-proof records of test runs and associated results) is an important security goal, it is beyond the scope of this document."documentedS4 · §5.1

§2

Where in a pipeline it is made

factkindsource
The DoD stage list: "These activities happen at different test stages": "Development stage: unit test, SAST discussed in the build phase."; "System test stage: DAST or IAST, integration test, system test."; "Pre-production stage: manual security test, performance test, regression test, acceptance test, container policy enforcement, and compliance scan."; "Production stage: operational test and evaluation with mission users." Then: "Test audit happens at all stages."documentedD4 · §3.5
"Continuous integration (CI) executes automated tests such as unit tests and Static Application Security Test (SAST), verifying the integrity of the work in the broader context of the artifact or application." "When the CI completes, the artifact is automatically promoted to the test environment." Tests there that "complete without error" let the artifact "pass through another control gate".documentedD6 · p. 9
The reference design: "as code is checked into a branch it triggers the CI/CD pipeline workflow and resulting automated build, SAST, DAST, unit, and other relevant tests are executed." "If all of these relevant tests are successful, then the artifact is deployed into the test environment."documentedD8 · §4.1
Where test results are read: the release decision. Inputs to "Release go / no-go decision" (REQUIRED, SSDF PW.2.1, RV.3.4): "Design documentation; Version controlled artifacts; Version controlled test reports; Security test and scan reports". Output: "go / no-go decision; Artifacts are tagged with release tag if go decision is made".documentedD4 · Table 8; D8 · Table 10
On pull requests: "PULL-PUSH_REQ-1: The project maintainer should run automated checks on all artifacts covered in the change being pushed, such as unit tests, linters, integrity tests, security checks, and more."documentedS4 · §5.1.2
Process attestation in a build "pertains to the computer programs that transformed the original source code or materials into an artifact (e.g., compilers, packaging tools) and/or the programs that performed testing on that software (i.e., code testing tool)."documentedS4 · §5.1.1
NSA and CISA: in CI, "the developer’s changes are validated by creating a build and running automated tests against the build."documentedG2 · Key terms
The ESF guide's nightly build: "nightly builds should be performed that include manual and automated security and regression tests." "Artifacts such as logs and automated email notifications sent when regression tests fail help notify and track where and when problems arise." It separates these from "a developer’s own automated unit test, which may run manually during coding and automatically during the “building” of the component".documentedG1 · §2.2.1, item 3

§9

Relationships

  • Coverage. Made by the same run (both clubstraylight.com and springboard upload it from the test job). SP 800-204D asks that "SAST and DAST tools … be run in CI/CD pipelines with code coverage reports being provided to developers and security personnel" (S4 · §5.1.4); SA-11(8)'s discussion and STIG V-222649 carry it. Shared controls: SA-11, SA-11(8).
  • Static analysis and vulnerability scan. The other outputs of PW.7 and PW.8. Shared controls: SA-11, SA-15(7), and in the 1.2 draft RA-5 and SI-2. The DoD tables list them beside the test rows (§5).
  • Attestation, timestamp, evidence manifest. A test result carries no integrity of its own; in the portfolio it is hashed inside the zip the attest job anchors, and springboard's manifest lists it with a SHA-256. PO.4.2 Example 4 asks to "prevent any alteration or deletion of the information."
  • Provenance. SP 800-204D's process attestation includes "the programs that performed testing on that software" (§2).
  • OSCAL. springboard's SSP fragment states SA-11 from the test job's existence (§8, §10).
  • Audit events. springboard's audit-event-test.json records the test job's status, run id, and commit; the DoD "Test Audit" row is the same record at its grain.
  • SBOM. The DoD Operations Team Acceptance reads both; the cATO criteria let SBOMs be kept beside "results of security tests" (§5). The SBOM jobs in clubstraylight.com and springboard wait on test (SBOM §10).

§10

Observed

  • The DoD guidebook and its tables align Regression, Software Integration, System, and Component tests with "RV.8.1, RV.8.2". Neither SSDF 1.1 nor the 1.2 draft has an RV.8; RV ends at RV.3.4 in 1.1, and a search of the 1.2 draft for "RV.8" and "RV.4" finds nothing (2026-11-14).
  • springboard's verify-evidence.js glosses its "standard" retention class for test results as "GRS 2.7". GRS 2.7 is "Employee Health and Safety Records" (R2 · p. 1). The schedule whose text includes "verification and testing" is GRS 3.1 item 011 (§6), whose disposition is five years after the system is superseded, not 90 days (2026-11-14).
  • springboard's oscal job downloads only gitleaks-report, npm-audit, and trivy-results. The SA-11 statement in its SSP fragment is fixed text, not derived from surefire-reports; the skill's pitfall "SSP claims evidence that the bundle does not contain" is met only because verify-evidence separately requires the directory (reading of the workflow, 2026-11-14).
  • springboard's frontend unit tests leave no per-test file: karma.conf.js sets reporters: ['progress', 'kjhtml'], so their results are in the job log only; coverage is written. Playwright has no JSON or JUnit reporter configured (2026-11-14).
  • springboard's and clubstraylight.com's attest.mjs zip only regular files at the top of ci-artifacts/. With merge-multiple: true, Playwright's per-test directories and the HTML reports' subdirectories are left out of the zip, and the HTML reports' top-level index.html files land on one path. Which survives was not checked in a run (reading, 2026-11-14).
  • The three pipelines differ on failing runs. slacronym attests every run when the bucket is set, failures included. clubstraylight.com and springboard attest only after the checks pass on the main branch, so a failing run's results exist only as a 90-day GitHub artifact (reading, 2026-11-14).
  • clubstraylight.com's RSpec JSON (local copies under tmp/test-results/, run date not recorded) carries "version":"3.13.6", a seed, one object per example, and summary_line "914 examples, 0 failures" (audit) and "506 examples, 0 failures" (graph). It has no commit and no timestamp; the commit is in attestation.json beside the zip. The skill asks that every evidence file "preserve generator identity, timestamp, scope, and run context" (2026-11-14).
  • CSL-0230's nine S3 objects are the six artifact files (bundler-audit-results.txt, two RSpec JSON, two coverage JSON, the SBOM) plus the zip, the PDF, and attestation.json (arithmetic, 2026-11-14).
  • The cicd-golden-pipeline skill's SSDF table maps PW.8 to "Vulnerability scan (Trivy)" and cites the ASD STIG as V6R3. NIST's mapping of PW.8.1 and PW.8.2 is to SA-11 and its enhancements, and the DoD tables align unit, functional, and integration tests with PW.8.1 and PW.8.2 (2026-11-14).
  • SP 800-53A's extracted text drops the "ti", "fl", "ft" and "ffi" ligatures ("tesng", "ﬂaw"); quotations on this page restore them from the printed words (2026-11-14).
  • The implementation guide's Table 2 extracts its ID, Description, and Level columns separately; the levels for SA07 and SA10 are read by row order (2026-11-14).
  • V6R5 writes "DoW" where earlier releases had "DoD", for example V-222645, "prior to deploying to DoW operational networks" (2026-11-14).
