Atlases · CI/CD · secrets scan

Secrets scan

A secrets scan report is the record a scanner writes after searching a repository's files, and with full history its past commits, for credentials committed to it: passwords, keys, and tokens. It states what was scanned, with which tool and version, and each match with its rule, file, and line. This page records how the issuing documents describe the practice (§1), where a pipeline runs it (§2), the NIST, STIG, and DoD text that bears on it, and what the three portfolio repositories run (§8). §3.3 checks springboard's "PW.6" label against SSDF PW.6.

§1

What a secrets scan report is

None of the documents read defines the report as a term. They define what is searched for, the search, and its output.

factkindsource
What a secret is, in a pipeline: "Secrets (e.g., private keys and passwords) are required for authentication between tools and in the build and deployment process to ensure deployed resources have access."documentedG1 · Exposure of secrets
The ESF's list: "Secrets can be but are not limited to account passwords, API keys, and private certificates."documentedG2 · §2.4.1, p. 31
SP 800-53's term is the authenticator: "Authenticators include passwords, cryptographic devices, biometrics, certificates, one-time password devices, and ID badges. Device authenticators include certificates and passwords."documentedS2 · IA-5 discussion
The requirement the scan checks, as a control: "Ensure that unencrypted static authenticators are not embedded in applications or other forms of static storage." Its discussion: "In addition to applications, other forms of static storage include access scripts and function keys."documentedS2 · IA-5(7)
The search, as a pipeline task: "Evaluate committed code for adherence to organizational policy, including the absence of secrets such as keys and Application Programming Interface (API) tokens."documentedS4 · §5.1.4, COMMIT-REQ-1
The output. DoD's activity "Code commit scan" has as input "Locally committed source code" and as output "Security findings and warnings". SP 800-204D: "The detected secrets should be displayed prominently through media such as security dashboards, and appropriate alerts should be generated upon detection of policy violations with documented methods to remediate violations."documentedD7 · Table 5; S4 · §5.1.4
What a report holds, from the portfolio's tooling: the minimum evidence content is "tool name and version", "scan scope (full history vs working tree)", "repository, ref, and commit SHA", "execution timestamp", and "explicit findings array, even when empty". Each gitleaks finding is read for its RuleID, File, StartLine, and Description.portfoliodave-skills · skills/cicd-golden-pipeline/SKILL.md §1 · 96d1f33; springboard · scripts/generate-oscal.js · b2fdcb9
The assessor's view. SP 800-53A lists, among the objects to examine for IA-5(7), "application code reviews for detecting unencrypted static authenticators" (S6 · IA-05(07)-Examine). A secrets scan report is an automated instance of that object.

§2

Where in a pipeline it is made

The sources place the scan at four points, from the developer's machine to the final package.

1Before commitDoD, Develop phase, "Code commit scan", REQUIRED: "Check the changes for sensitive information before pushing the changes to the main repository. If it finds suspicious content, it notifies the developer and blocks the commit." ESF: "Performing static analysis to scan for secrets before commit and during CI/CD blocks secrets from the code base."
2At pushSP 800-204D: "One SSC security measure required during code commits is the prevention of secrets getting into the committed code. This is enabled by a scanning operation for secrets and results in a feature called push protection".
3Before deploySP 800-204D, DEPLOY-REQ-1: "For code that is already in the repository and ready to be deployed, a security scanning sub-feature should be invoked to detect the presence of secrets in the code, such as keys and access tokens."
4Final packageESF: the package "may contain confidential information (e.g., hard coded credentials, personal data)"; a binary composition tool "can detect potential vulnerabilities and threats – including software of unknown provenance (SOUP) and secrets inadvertently included in the final packages – and produce an SBOM of the final package for the customer."
factkindsource
The four steps above, by source and place.documentedD7 · Table 5; G2 · §2.2.1, mitigation 2, §2.5; S4 · §5.1.4, §5.2
Why the whole history: "In many instances, the repository should be scanned for the presence of secrets, even before being populated with code, since their presence in a repository can mean that the credentials are already leaked, depending on the repository’s visibility."documentedS4 · §5.2, DEPLOY-REQ-1
DoD lists the scan as a continuous security activity in the Develop phase, with the tool dependency "Source code repository security plugin", separate from "Static code scan before commit" (IDE security plugins) and from SAST in Build and Test.documentedD7 · Table 1
The threat. NSA and CISA list "Exposure of secrets" among the risks: "Security key compromise and insecure secrets management within the pipeline, such as hardcoding access keys or passwords into infrastructure as code". SP 800-204D lists "Stealing secrets by submitting merge requests" among exploits, and among non-malicious actors "a software engineer who inadequately manages secrets through a lack of tooling or purposeful subterfuge for ease of use."documentedG1 · p. 6; S4 · §3.1.2, §3.1.5
The mitigation beside the scan: "Never pass secrets in plaintext anywhere in the pipeline. Ensure secrets (e.g., passwords and private keys) are never left embedded in software where they can be reverse-engineered out." "Most modern CI/CD tools come with a secrets management solution, which means a CI/CD tool can securely store the secrets and pass them using an indirect reference within the pipeline".documentedG1 · Secure secrets
The ESF, for the build pipeline: "avoid putting secrets in plain text in any code (e.g., automation code), avoid logging sensitive data in application logs, and regularly rotate secrets."documentedG2 · §2.4.1, p. 31

§3

NIST: SSDF tasks, SP 800-53 controls, and the PW.6 label

Each control below also requires a process (who may hold an authenticator, how a compromised one is revoked, how findings are triaged), so a scan report is evidence toward the control and does not meet it alone. The first table is NIST's mapping, from the SSDF's reference column. The second quotes the controls; its "basis" column says whose mapping each row is.

3.1 The SSDF tasks

The word "secret" does not occur in SSDF 1.1 outside "Secretary"; its one use of "credential" is PW.1.1 Example 2, which asks for more rigorous risk assessment of "identification, authentication, and access control, including credential management." SSDF 1.2's one use of "secret" is PW.9.1 Example 2, new in the draft (S5 · App. B). No SSDF task in either version calls for a secrets scan by that term, so the rows below are the tasks whose text covers it, with the basis stated.

3.3 The PW.6 label checked

springboard's job is titled "Secrets Scan (PW.6)" and its audit event carries "stage":"PW.6"; the label comes from the shared skill's table, which pairs PW.6 with "Secrets scan" (§8). The check is against what PW.6 says.

factkindsource
PW.6 is "Configure the Compilation, Interpreter, and Build Processes to Improve Executable Security (PW.6): Decrease the number of security vulnerabilities in the software and reduce costs by eliminating vulnerabilities before testing occurs."documentedS1 · p. 14
Its two tasks: PW.6.1 "Use compiler, interpreter, and build tools that offer features to improve executable security." PW.6.2 "Determine which compiler, interpreter, and build tool features should be used and how each should be configured, then implement and use the approved configurations." The ten examples concern tool versions, change management and integrity of the tools, compiler warnings, the "clean build", a controlled build environment, randomized execution characteristics, and approved configurations as code. None concerns credentials. The 1.2 draft keeps the text and changes only the SP 800-53 references.documentedS1 · p. 14; S5 · p. 29
NIST's own CI/CD guide reads PW.6 the same way: its Table 2 gives "5.1.1 Secure Build (Addresses the requirements for PW.6 through security requirements for the build platform)". The secrets requirements are in §5.1.4 and §5.2, not §5.1.1.documentedS4 · App. A, Table 2
DoD gives the same activity a different task: "Code commit scan", REQUIRED, SSDF "RV.1.2".documentedD7 · Table 5
Finding: the text of PW.6 and its tasks does not cover a secrets scan, and the two government documents that place the scan put it elsewhere (SP 800-204D under commit and deploy requirements, DoD under RV.1.2). The SSDF texts that cover it are RV.1.2 (DoD's assignment), PW.7.2 Example 6 (this page's reading), and, for the shipped software, PW.9.1 Example 2 of the 1.2 draft. A label of "RV.1.2" with "PW.7.2" would match the sources read; "PW.6" matches none.observed2026-11-14, from the rows above
The label's effect on NIST's control mapping: PW.6 maps to SA-15 (and SR-9, and in 1.2 CM-02, CM-09, SC-38); PW.7.2 and RV.1.2 map to SA-11 and, for PW.7.2, SA-11(1). An evidence store that follows the label files the report under the build-tool controls rather than the developer-testing ones.observed2026-11-14; S1, S5 reference columns

factkindsource
Tool quality: "The complexity and thoroughness of these static scanning technologies vary greatly."documentedG2 · §2.2.1

§9

Relationships

  • Static analysis. The ESF calls the secrets scan "static analysis to scan for secrets"; DoD lists it as a separate activity from SAST, with its own tool. Both rest on PW.7.2 and SA-11(1) in NIST's mapping (§3).
  • Vulnerability scan. springboard's oscal job waits on both scans and reads both reports; the vulnerability scan's findings go to RA-5, the secrets scan's to SI-3 (§8). RV.1.2, DoD's task for the secrets scan, maps to SA-11 and in the 1.2 draft also to RA-5.
  • Audit events. The "PW.6" label is carried in audit-event-secrets-scan.json (§3.3).
  • OSCAL. The assessment results take gitleaks findings as SI-3 observations; with the report as written they never receive one (§10).
  • Evidence manifest. Hashes the report and fails the run if it is missing.
  • Attestation and timestamp. The report is inside the zip whose hash is attested and timestamped on master pushes.
  • SBOM. The ESF gives one tool, binary composition analysis of the final package, both jobs: finding "secrets inadvertently included in the final packages" and producing "an SBOM of the final package". The SBOM's SSDF tasks (sbom.html §6) share no control with this page's.
