OSCAL documents

OSCAL, NIST's Open Security Controls Assessment Language, is a set of JSON, XML, and YAML models for control catalogs, baselines, system security plans, assessment plans, assessment results, and plans of action. A pipeline that emits OSCAL writes its scan results and its claims about controls in those models. This page records the models a pipeline uses, the NIST, STIG, Department of Defense, and OMB documents that bear on them, and what springboard's pipeline writes: three documents per run, read line by line against the OSCAL 1.1.2 schema. The control mappings in §3 state whose each is.

Every document's metadata requires "title", "last-modified", "version", "oscal-version". OSCAL identifiers are UUIDs: "A type 4 ('random' or 'pseudorandom') or type 5 UUID per RFC 4122."documentedX3 · #assembly_oscal-metadata_metadata, UUIDDatatype
NIST publishes SP 800-53 itself in OSCAL. The catalog's controls carry their SP 800-53A assessment objectives as parts: RA-5's objective has the id ra-5_obj and the label "RA-05" with class "sp800-53a", and its sub-objectives are ra-5_obj.a onward.documentedS6 · ra-5_obj
SP 800-53A Rev. 5 lists "Open Security Controls Assessment Language; OSCAL" among its keywords and publishes its assessment procedures "in multiple data formats, including comma-separated values (CSV), plain text, and Open Security Controls Assessment (OSCAL)". "The CSV, plain text, and OSCAL formats represent derivative formats of the (normative) assessment procedures in this publication."documentedS8 · Keywords, Supplemental Content
A baseline is an OSCAL profile over the catalog. The moderate baseline profile is titled "Electronic (OSCAL) Version of NIST Special Publication 800-53 Revision 5.2.0 MODERATE IMPACT BASELINE" and selects 287 control and enhancement ids (counted 2026-11-14).documentedS7 · metadata.title, include-controls
What the three portfolio documents hold. An assessment results document holds observations (what a tool saw) and findings (whether a control objective is satisfied), each tied to a control objective id from the catalog. A component definition describes a component. A system security plan describes the system, its information types and impact levels, its baseline, and how each control is implemented. §8 records what springboard's three documents put in each.

NIST: SSDF tasks, SP 800-53 controls, SP 800-53A

OSCAL documents are evidence toward a control; each control also asks for a process, an assessor, a plan, and a review that no generated file supplies. No SSDF task cites OSCAL (searched, SSDF 1.1 and the 1.2 draft). SP 800-53A: assessment objects, methods, findings

factkindsource
The examine objects for RA-5 include "assessment report", "vulnerability scanning results", and "system security plan".documentedS8 · RA-05, p. 432
For CA-2: "control assessment plan; control assessment report; system security plan". For CA-5: "control assessment report; control assessment evidence; plan of action and milestones". For CA-7: "control assessment report; plan of action and milestones; system monitoring records; ... status reports; system security plan". For PL-2: "system security plan".documentedS8 · CA-02, CA-05, CA-07, PL-02
The three assessment methods are "Examine", "Interview", "Test". Test is "The process of exercising one or more assessment objects under specified conditions to compare actual with expected/desired behavior". OSCAL's observation methods are the same three, with "UNKNOWN".documentedS8 · App. C, p. 713; X3
"Each determination statement contained within an assessment procedure executed by an assessor produces one of the following findings: satisfied (S); or other than satisfied (O)." OSCAL's finding states are "satisfied" and "not-satisfied".documentedS8 · §3.3, p. 31; X3
An assessment report's key elements include "Security categorization", "Assessor's name/identification", "Selected assessment methods and objects", and "Assessment finding summary (indicating “satisfied” or “other than satisfied”)". "Whenever possible, automation is used to make assessment data collection and reporting cost-effective, timely, and efficient."documentedS8 · App. E, pp. 718–719

§10

Observed

Read 2026-11-14 from the files at the commits in §8 and the schema of X3. No OSCAL validator was run; the schema checks below are by reading its required lists, enums, and additionalProperties: false against the objects the script builds.

  • The three documents carry every member the 1.1.2 JSON schema requires, and no member the schema does not define. Their enum values ("TEST", "finding", "objective-id", "satisfied", "not-satisfied", "under-development", "this-system", "implemented") are among the schema's. The deterministic UUIDs (lines 33–44) have version digit 4 and variant 8 to b, which the schema's UUID pattern accepts. On this reading the files are schema-valid; the script's claim that they are "accepted by the NIST OSCAL viewer at oscal.io" was not checked.
  • The oscal job runs only when secrets-scan and vulnerability-scan succeed. gitleaks, the npm audit at high, and the Trivy gate each fail their job on a finding at the configured level, so a run with such a finding writes no assessment results. In a run that writes them, the gitleaks and Trivy inputs carry no vulnerabilities (the Trivy JSON uses the gate's filters), and the only possible not-satisfied findings are npm advisories below high. The SI-3 branch of the script is unreachable in this pipeline.
  • Every finding targets a whole objective (ra-5_obj, si-3_obj), where SP 800-53A makes a finding per determination statement and the catalog carries ra-5_obj.a onward. SI-2, SA-11, and SA-15 are reviewed controls with no finding.
  • The assessment plan import-ap points to is a back-matter resource whose one link is the repository's web page. The #…-evidence fragment links point to nothing in the document. The observation subjects are the component-definition's UUID, which differs from the SSP's this-system component UUID; the assessment results import neither document.
  • The component-definition's responsible role provider is defined in no roles list.
  • The SSP's system-ids declares the RFC 4122 (UUID) identifier type for the value owner/repo, which is not a UUID. Its categorization system is https://doi.org/…; the value the schema lists is http://doi.org/10.6028/NIST.SP.800-60v2r1. The https form passes through the schema's generic URI branch.
  • SP 800-60 type C.3.5.8 is "System and Network Monitoring Information Type", "Security Category = {(confidentiality, Moderate), (integrity, Moderate), (availability, Low)}" (S9 · p. 100). The SSP's three impact levels are that type's provisional ones; the information it describes is "Synthetic todo data".
  • The SSP imports the moderate profile from the main branch. On 2026-11-14 that file is release 5.2.0 and declares oscal-version 1.2.3; the SSP declares 1.1.2. The profile selects 287 ids; the SSP describes three, and PL-2's "supporting rationale" for the categorization has no member in it.
  • The assessor party is the repository itself. The moderate baseline includes CA-2(1), "Employ independent assessors or assessment teams to conduct control assessments", and the cATO criteria ask for "Independent verification of assessment plans and evidence".
  • verify-evidence's permanent class cites GRS 5.1 and DAA-0567. GRS 5.1's items are temporary and DAA-0567 occurs in none of the four GRS copies read; GRS 3.2 item 010, which lists system security plans and vulnerability assessments, is temporary.
  • The shared skill dates M-24-15 "(June 2024)" and links a /2024/06/ address; the memorandum is dated July 25, 2024 and served from /2024/07/. The skill shows oscal as needing vulnerability-scan alone; springboard's job also needs secrets-scan.
