How Claude Code decides whether a tool call runs

Every Bash command, file edit, web fetch, and MCP call passes through one ordered evaluation before it executes. This page is that evaluation, then the rule syntax, then how permissions relate to modes, hooks, the sandbox, and the settings files they live in.

1 · the evaluation order

Seven gates, top to bottom, first decision wins

The documentation states the order of the rule gates in one sentence and the position of hooks, safety checks, and modes in separate sections. This table joins them. A gate that does not decide passes the call down.

1PreToolUse hooksRun before the permission prompt for every tool except EndConversation. Exit code 2 stops the call "before permission rules are evaluated", so a hook can block what an allow rule would pass. A hook that returns allow does not skip gates 2 and 3.D1 · Extend permissions with hooks

Where gate 4 sits is a reading, not a quotation. The documentation says the protected-path check "runs before Claude Code evaluates allow rules from settings" and that in auto mode allow rules resolve first except for those two checks. It does not state where the checks sit relative to ask rules. 3 · the three rule types

allow, ask, deny

All three live under the permissions key of a settings file, each an array of Tool or Tool(specifier) strings. D1 · Permission rule syntax

RuleEffectDetailSource
allow"Let Claude Code use the specified tool without manual approval."Checked last. Uses each tool's own specifier syntax; parameter matching (Tool(param:value)) is not accepted for allow. No effect in bypassPermissions. Project-file allow rules wait for workspace trust (§8).D1 · Manage permissions; D1 · Match by input parameter; D2 · Available modes
ask"Prompt for confirmation whenever Claude Code tries to use the specified tool."Beats a narrower allow. Prompts in every mode; denied in dontAsk. A deny or ask rule whose tool name matches no known tool warns at startup (names with _ or * exempt).D1 · Manage permissions; D1 · Tool name wildcards
deny"Prevent Claude Code from using the specified tool."Beats everything from any scope. Bare name (Bash, or the equivalent Bash(*)) removes the tool from context; scoped (Bash(rm *)) leaves the tool and blocks matching calls. A broad deny cannot carry allowlist exceptions. "A broad deny rule like Bash(aws *) blocks every matching call, including calls that also match a narrower allow rule like Bash(aws s3 ls)." Write the deny narrower, or move the exception to a hook. D1 · Manage permissions

The /permissions dialog lists every rule and the settings file it came from, and a change made there applies from Claude's next tool call in the same turn (before v2.1.234 it waited for the turn to end). D1 · Manage permissions

Where a session's starting mode comes from

First match wins: the --permission-mode flag or --dangerously-skip-permissions; then permissions.defaultMode in a settings file; then the built-in default. A project's .claude/settings.json or settings.local.json cannot set auto (the value is ignored and the built-in default is used, not the user file's value) or bypassPermissions (ignored; the session starts in Manual). The built-in default is auto on Pro, Max, and Team in a terminal or VS Code, and default for claude -p, the SDK, Enterprise, API keys, cloud providers, a first session after install or upgrade, or when any settings file sets disableAutoMode to "disable". D2 · Which mode a session starts in

Locking a mode out. permissions.disableBypassPermissionsMode and permissions.disableAutoMode set to "disable" work from any settings file; in managed settings they cannot be overridden. A running auto-mode session leaves auto when the managed setting reaches it (from v2.1.251; before, it kept auto until the session ended). 5 · rule syntax and wildcards

Matching, wildcards, and the traps

Rules are Tool or Tool(specifier). Parentheses inside the specifier are literal. A bare tool name matches every use; Bash(*) is equivalent to Bash. D1 · Permission rule syntax

Bash wildcards

"A * in a Bash rule matches any text, including spaces." The vendor's own table, reproduced in full:

Bash(npm run build)npm run buildnpm run build --watch

D1 · Wildcard patterns, table reproduced verbatim

Rule of thumbWhat the documentation saysSource
Put the * after the subcommandEverything before the first * is matched as written, so those words limit the rule: Bash(git log *) allows only git log; Bash(git *) allows every git command. An allow rule with a * before the subcommand, such as Bash(git * main), warns at startup; it also matches -c, which makes git run a program you name.D1 · Wildcard patterns (warning)
A trailing * after a space also matches the bare commandBash(ls *) matches ls. Only when the trailing * is the rule's sole wildcard: Bash(* --help *) does not match npm --help.D1 · Wildcard patterns
The space before a trailing * is part of the ruleBash(ls *) requires a space, so lsof does not match; Bash(ls*) matches lsof too.D1 · Wildcard patterns
The :* suffixEquivalent to a trailing *; recognised only at the end of a pattern. In Bash(git:* push) the colon is literal. The permission dialog writes the space-separated form when you choose "don't ask again" for a prefix.D1 · Wildcard patterns
Tool-name globsDeny and ask rules accept globs in the tool-name position, matching the full name: "*" every tool, "mcp__*" every MCP tool. A bare-name glob deny removes the matched tools from context (EndConversation exception applies). Allow rules accept globs only after a literal mcp__<server>__ prefix; an unanchored allow glob is skipped with a warning.D1 · Tool name wildcards
Canonical names, not labelsRules match the canonical tool name; the transcript label can differ (Stop Task is TaskStop). A deny or ask rule naming an unknown tool warns at startup.D1 · Tool name wildcards

Match a parameter, not the content

Deny and ask rules can match a top-level input parameter on any built-in tool with Tool(param:value): Agent(model:opus), Agent(isolation:worktree), Bash(run_in_background:true). One parameter per rule; * allowed in the value; an omitted parameter never matches; the value is compared before normalisation. A tool's primary content field cannot be matched this way (command, file_path, path, notebook_path, url); Bash(command:rm *) is ignored with a startup warning. MCP parameter rules go through --disallowedTools; a settings-file mcp__ rule with parentheses is skipped and listed in the invalid-settings dialog. D1 · Match by input parameter

6 · bash rules in depth

Compound commands, wrappers, what a rule does not match

BehaviourWhat the documentation saysSource
Compound commands are splitSeparators &&, ||, ;, |, |&, &, and newlines. An allow rule must match each subcommand on its own. Deny and ask rules fire if any subcommand matches, including inside a subshell, a command substitution, or a loop body, even in auto mode. A dangling && makes the command unparseable, so no allow rule approves it. "Don't ask again" on a compound saves one rule per subcommand needing approval, up to five.D1 · Compound commands
Wrappers are strippedtimeout, time, nice, nohup, stdbuf, the builtins command and builtin, zsh noglob, and bare xargs (not xargs -n1). Not stripped: command -v, nocorrect. A leading assignment of a known-safe environment variable is stripped for allow rules; deny and ask rules match past any leading assignment. The list is not configurable.D1 · Wrappers
Environment runners are not wrappersnpx, docker exec, devbox run, direnv exec, mise exec: Bash(devbox run *) matches whatever follows run, including devbox run rm -rf .. Write one rule per inner command, such as Bash(devbox run npm test).D1 · Wrappers
Exec wrappers cannot be prefix-approvedwatch, setsid, ionice, flock, and find with -exec or -delete always prompt in Manual mode under a prefix rule; an exact-match rule for the full command approves one invocation.D1 · Wrappers
A rule matches the text, not the programBash(git push *) in deny stops git push origin main and not git -C . push origin main, git -c push.default=current push origin main, or git 'push' origin main. Bash(rm *) does not stop /bin/rm or bash -c 'rm …'. "A deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." Use the sandbox or a PreToolUse hook for a boundary.D1 · What a Bash rule doesn't match
Argument-constraining rules are fragileBash(curl http://github.com/ *) misses options before the URL, https://, redirects, and URL=… && curl $URL. The documented alternatives: deny curl and wget and route through WebFetch(domain:…) paired with the sandbox network allowlist; a PreToolUse hook that validates URLs; CLAUDE.md guidance as a nudge only.D1 · Read-only commands (warning)
Read-only commands never promptBuilt in, not configurable: ls, cat, echo, pwd, head, tail, grep, find, wc, which, diff, stat, du, cd, and read-only forms of git. Exceptions that still prompt in Manual mode: unquoted globs on commands with write-capable flags (find, sort, sed, git); docker aimed at another daemon; file with path-opening flags; Windows UNC paths; anything the parser cannot fully parse, and any command over 10,000 characters. cd into a working directory is read-only, but cd then git into a different directory prompts (that directory's hooks could run), as does cd with a redirect whose target cannot be resolved. An ask or deny rule forces a prompt for any of these.D1 · Read-only commands
Redirections are checked as file access> file, >> file, 2> file are checked against Edit rules, protected paths, and the working directories; a target starting with ~ or containing a glob needs approval. < file is checked against Read rules and the working directories (from v2.1.257). /dev/null, descriptor forms like 2>&1, here-docs and here-strings are not checked. A rule such as Bash(git commit *) allows the command, not the target.D1 · Redirections

8 · settings scopes and precedence

Where rules live, and who wins

Permission rules follow the same precedence as every other setting, with one rule stacked on top: a deny at any level wins. D1 · Settings precedence; D3 · Settings files and precedence

highestManaged settingsmanaged-settings.json, MDM, or the claude.ai console. "No other level, including command line arguments, can override a managed permission rule." Home of allowManagedPermissionRulesOnly, which makes managed settings the only source of rules.
↓Command lineclaude --settings, --allowedTools, --disallowedTools. Can add restrictions beyond managed settings; cannot lift a managed deny.
↓.claude/settings.local.jsonYour own project overrides, where "don't ask again" approvals are saved. Stored at the git repository root from v2.1.211 (resolved through worktrees to the main checkout); before, in the starting directory.
↓.claude/settings.jsonShared project settings, checked in. Its allow rules and additionalDirectories wait for workspace trust.
lowest~/.claude/settings.jsonYour user settings, every project. /path rules here anchor at ~/.claude/.

D3 · Settings precedence (the five levels, verbatim order); D1 · Settings precedence; D1 · Permission system

"If a tool is denied at any level, no other level can allow it": a managed deny is not overridden by --allowedTools; a user-level deny blocks a project-level allow and a project-level deny blocks a user-level allow, "because deny rules from any scope are evaluated before allow rules". Allow rules are merged across scopes unless allowManagedPermissionRulesOnly is set. D1 · Settings precedence; D3 · line 722

Workspace trust

"permissions.allow rules and permissions.additionalDirectories entries in a project's .claude/settings.json grant capability, so Claude Code applies them only after you accept the workspace trust dialog." Deny and ask rules are not gated. Trust is keyed on the git repository root (the main checkout for a worktree), or the starting directory outside a repository, and is session-only when started in the home directory. A claude -p or SDK run never shows the dialog: project allow rules are not used there and a warning goes to stderr. D1 · Project allow rules and workspace trust; D1 · What runs before you trust a folder

.claude/settings.local.json normally needs no trust step. When it is tracked in git, or .claude is a symlink, it is treated as repository-supplied and held until trust; the git check runs only after trust, so before that the file's rules are applied at once only in your configuration home. From v2.1.207; in v2.1.196 to v2.1.199 the rules were held in the configuration home too. D1 · When your local settings file needs trust

9 · the layers around the rules

Hooks and the sandbox

10 · protected and critical paths

Two checks that outrank allow rules and hooks

Protected paths

"Writes to a small set of paths are never auto-approved, except in bypassPermissions mode and in planning sessions with bypass permissions available." Allow rules in settings do not pre-approve them; the check runs before allow rules from settings. In modes that prompt, the prompt for a .claude/ write offers a session-wide grant for later .claude/ writes. Under --restricted (v2.1.248+) the classifier cannot approve them. D2 · Protected paths

Critical paths

"Claude Code never lets a permissions.allow rule or a PreToolUse hook that returns "allow" approve an rm or rmdir command that targets a critical path, even in modes that skip other prompts." A matching deny still blocks outright. Critical: the filesystem root and its direct children, the home directory, Windows drive roots and their top-level directories, the working directory and its parents, and additional directories and their parents when the removal is a glob under them. A glob or trailing slash directly under a shell variable (rm -rf "$DIR"/*) counts, since an empty variable makes it a root removal; hiding the removal in $(…) or <(…) does not skip the check. 13 · gaps and unverified claims

What this page does not know

  • unverified The exact position of the protected-path and critical-path checks relative to ask rules (§1 note). Outcomes are documented per mode; ordering against ask is inferred.
  • unverified Whether an allow rule can override plan mode's block on edits. D2 says edits "stay blocked until you approve the plan" and does not mention allow rules there. The operator's draft asserted "regardless of allow rules"; this page does not.
  • Not covered here: the hooks contract itself (events, input JSON, output fields, exit codes), the auto-mode classifier's block and allow lists in full, sandbox configuration, the Agent SDK's permission options, managed-settings delivery and the managed-only keys, and the behaviour of Cowork, cloud, and Remote Control sessions beyond the rows that name them. Each is a page of its own.
  • Not tested by the family at this version: none of the facts above were re-run against v2.1.268; the three observations in §12 predate it. The documented and observed marks are therefore about sources, not about a fresh test.
  • Version-gated facts keep their version on the row. A reader on an older client should check each such row before relying on it.

Corrections to the draft: (1) it said bypassPermissions made protected-path writes an exception; D1 and D2 say bypass skips those prompts, and the exceptions are the "actions no mode auto-approves".
