Harness atlas · Codex CLI · permissions

How Codex decides whether a command runs

Every shell command Codex spawns passes through two controls: a sandbox that bounds what the command can touch, and an approval policy that says when Codex must stop and ask. Execution-policy rules, hooks, and a reviewer agent sit around the two. This page is that evaluation, then each control in depth, then the files they live in and how they relate to the Claude Code permissions page.

1 · the two controls

A sandbox says what a command can touch; an approval policy says when Codex asks

"Codex security controls come from two layers that work together": the sandbox mode, "What Codex can do technically (for example, where it can write and whether it can reach the network)", and the approval policy, "When Codex must ask you before it executes an action". Either value of one combines with either value of the other. C1 · Sandbox and approvals

2 · the evaluation order

Six gates, top to bottom, as this page reads them

The documentation states each gate on its own page and never joins them in one sequence. This table is the author's joining; the position of each row is marked where the documents leave it open. A gate that does not decide passes the command down.

The reviewer

approvals_reviewer is user by default; auto_review means "eligible approval prompts go to a reviewer agent". "The reviewer evaluates only actions that already need approval", and "Automatic review, when available, doesn't change the sandbox boundary." The app and IDE menus call it Approve for me; the CLI flag --approve-for-me reads "Route approval requests through automatic review using the workspace-write sandbox" (observed, codex --help). MCP servers and apps carry their own reviewer setting, apps.<id>.approvals_reviewer, inheriting the top-level value; MCP and app tools carry a per-tool approval_mode of auto, prompt, writes, or approve. C2 · How permissions work; C1 · Automatic approval reviews; C6 · approvals_reviewer, mcp_servers

Where the untrusted policy went. Its two parts moved to different controls: the sandbox decides what runs without asking, and execution-policy rules name the commands that may leave it. A project that is not yet trusted gets a narrower start instead: Codex "may also start in read-only until you explicitly trust the working directory", and "Commands then require approval unless an execution-policy rule allows them." 6 · permission profiles

One named policy for filesystem and network, in place of the sandbox keys

"Beta. Permission profiles are under active development and may change." A profile is "a named policy that combines filesystem rules" with "network rules", and profiles "let you apply least-privilege boundaries to local commands Codex runs on your behalf." "Permission profiles do not compose with the older sandbox settings": a configuration sets either default_permissions with [permissions] tables, or sandbox_mode with [sandbox_workspace_write], never both. The vendor's own example, reproduced verbatim:

prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "Viewing PRs is allowed with approval",
    match = [
        "gh pr view 7888",
        "gh pr view --repo openai/codex",
        "gh pr view 7888 --json title,body,comments",
    ],
    not_match = [
        "gh pr --repo openai/codex view 7888",
    ],
)

C4 · Create a rules file (the vendor's comments omitted)

A rule matches the argument list, not the program. As on the Claude Code page, a prefix rule covers the invocation the model usually produces. The rules page says nothing about a program reached by another path (/usr/bin/git, sh -c '…'); the sandbox, not the rule, is the boundary for those. unverified as to how an unsplittable script with a forbidden piece is decided beyond "treated as" one invocation.

Managed requirements

"Requirements constrain behavior; configuration values provide defaults." A requirements.toml delivered by an organisation sits above the ladder and narrows what any layer may choose: allowed_sandbox_modes, allowed_approval_policies ("such as on-request, never, and granular"), allowed_approvals_reviewers, allowed_permission_profiles, allowed_web_search_modes, allow_login_shell, allow_managed_hooks_only. "Omitted keys remain unconstrained." For local execution the order among managed sources is MDM and legacy managed-device requirements, then Agent Security, then the device's system requirements file. The network

"By default, the agent runs with network access turned off." In workspace-write it stays off "unless you enable it in your configuration" with sandbox_workspace_write.network_access = true; danger-full-access removes the network boundary with the filesystem one. A command network proxy (features.network_proxy, "experimental; off by default", and observed off at 0.162.0) adds per-domain allow and deny patterns, Unix socket allowlists, local-binding and SOCKS5 switches, and two keys prefixed dangerously_; the domain rules "apply only when the network proxy is active". Web search is a separate control: web_search is cached by default ("an OpenAI-maintained index without external access"), indexed, live, or disabled; under full access the default becomes live; the --search flag enables live search "(no per‑call approval)" (observed). C1 · Network access; C6 · sandbox_workspace_write.network_access, features.network_proxy, web_search; codex --help

Treat web results as untrusted. "Prompt injection can cause the agent to fetch and follow untrusted instructions." The vendor's guidance pairs the network boundary with a narrow sandbox rather than relying on either alone. C1 · Network access
